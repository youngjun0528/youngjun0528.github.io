# Software Architect Basic

## 3. 설계 전략 고안하기

### 만족스럽게 설계하기

- 실험으로 해결하기
- 위험 요소 줄이기
- 문제를 단순화하기
- 빠르고 반복하고 빠르게 배우기
- 문제와 해결책을 동시에 생각하기

> 이성적인 판단만 하며 최적의 설계를 찾기 보다는 '이 정도면 괜찮다'고 할만큼 필요를 채워 만족감을 찾는 설계를 진행한다.

### 설계를 얼마나 우서해야 하는가

#### 설계 최적점

- 설계 비용과 재작업 사이 최적점
- 프로젝트 규모, 요구사항 변경 빈도, SW 복잡도 등에 따라 설계 최적점이 결정된다.

> 프로젝트 스케쥴의 요소 : 전체 프로젝트 시간 = 개발 시간 + 아키텍쳐 설계 계획 시간 + 재작업 시간

- 시스템의 규모가 클수록 초기설계에 투자하는 데서 얻는 이득이 커집니다.
- 시스템의 규모가 작으면 초기설계에 투자하는 데는 얻는 이득이 작아진다. 빠르게 개발하는 것이 이득
- 아키텍쳐 설계에 거의 투자하지 않으면 재작업 빈도가 높아져 비효율적이다.
- 아키텍쳐에 투자할 수록 재작업 빈도가 줄어든다.

### 위험 요소를 가이드로 삼기

#### 위험, 조건과 결과

- 위험 : 미래에 일어날 수 있는 나쁜 일에 대한 암시
- 조건 : 현재의 사실
- 결과 : 무언가 잘못되었 때 조건과 직접적으로 결부된 사항

#### 디자인 마인드셋

- 이해하기 : 문제 정이가 위험 요소인 경우, 이해관계자나 연관된 시스템에 대해 더 깊게 이해할 필요가 있는지 확인한다.
- 탐색하기 : 해결 방법이 위험 요소인 경우, 다른 대안이 있는지 탐색한다.
- 실현하기 : 커뮤니케이션이 위험 요소인 경우, 이해관계자들이 설계를 충분히 이해하고 설계도를 볼 수 있는지 확인한다.
- 평가하기 : 설계의 의사결정이나 설계의 전반적인 적합성이 위험 요소인 경우, 설계에 대한 의사결정이 필요한지 확인한다.

### 설계 계획 세우기

1. 설계의 판단 근거
2. 디자인 산출물
3. 일정
4. 위험요소
5. 개괄적인 아키텍쳐 디자인

## 4. 이해관게자와 공감하기

- 이해관계자
    - 소프트웨어에 관심이 있거나 관여된 사람
    - 이해관계자가 누구인지 알아내고 그들의 요구를 이해하는 일이 이키텍트의 역할
    - 이해관계자 맵
        - 이해관계자는 개인이 될수도 그룹이 될 수도 있다. 각각의 이해관계자가 어떠한 관계를 가지고 있는지 확인한다.
- 고객경험 아키텍쳐
    - 1단계 : 고객에게 무엇이 중요한지 판단한다. 기능적인 요구사항이나, 품질 속성, 사용 환경을 확인한다.
    - 2단계 : 고객의 요구사항으로 시스템을 설계하고 문서화해 프로토타입을 만든다.
    - 3단계 : 프로토타입을 기반으로 고객과 리뷰를 진행한다.
    - 4단계 : 고객의 피트백에 따라 설계를 수정하고 아키턱쳐를 만든다.

### 비즈니스 목표 탐색하기

#### 비즈니스 목표 선언문

- 주체
    - 구체적인 사람 또는역할, 이해관계자나 그룹을 지칭할 이름
- 결과
    - 이해관계자들의 요구를 측정 가능한 결과로 표현
- 맥락
    - 이해관계자들의 요구사항의 의미, 회피하고자 하는 위험 등을 명시한다.

## 5. 아키텍쳐 핵심 요구사항 알아내기

> ### 아키텍쳐 핵심 요구사항(ASR : Architecture Significant Requirements)
> 1. 제약 : 바꿀수 없는 결정사항, 대체로 이미 결정딘 사항을 받지만, 가끔 선택권이 있다.
> 2. 품질속성
> 3. 영향력 있는 기능 요구사항
> 4. 기타 : 시간, 지식, 경험, 내부규저 등 설계에 영향을 미치는 요소

### 제약으로 설계 선택지 줄이기

- 제약이란, 이미 정해져서 변경이 불가능한 설계상의 의사결정
- 기술적인 제약 : 소프트웨어 시스템에서 사용할 수 있는 기술에 대한 결정을 제한
- 비즈니스적인 제약 : 인력, 프로세스, 비용, 일정에대한 결정을 제한

### 품질속성 정의하기

- 품질 속성이란, 소프트웨어 시스템의 외부에서 볼 수 있는 특성과 그 시스템에 기대하는 동작이 무엇인지 설명

> 품질 속성과 요구사항
> - 기존의 소프트웨어 공학에서는 기능 요구사항과 비기능 요구사항으로 분류, 정의하였다.
> - 통상적으로 푼질 속성은 비기능 요구사항에 속한다.
> - 하지만, 아키턱쳐 설계시 기능, 제약, 품질 속성으로 분류하고 정의 하는 것이 명확하다.
> - 시스템의 기능의 정의하고, 제약 사항을 명시하고, 품질 속성에 따라 시스템의 동작 여부를 판단하기 때문이다.

#### 품질 속성 시나리오

아래 품질속성 시나리오는 통합 테스트의 일종이라고 판단한다.

1. 시스템이 어떠한 제약 환경 ( 일반적인 사용환경 또는 부하가 걸린 환경 등 ) 아래에서
2. 어떠한 요청 이벤트가 시스템으로 들어가고,
3. 이에 따른 시스템이 동작을 통해
4. 응답값을 발생한다.
5. 이 응답값이 정해진 기준에 따라 PASS/FAIl 을 결정한다.

> 이미지
> 1. 자극 : 시스템의 시작점으로 요청 이벤트
> 2. 자극원 : 자극(요청)을 발생시키는 사용자 또는 외부 시스템
> 3. 산출물 : 시스템의 전체 또는 일부 컴포넌트, 시나리오의 대상
> 4. 반응 : 시스템의 마지막으로 응답 이벤트
> 5. 반응 측정 : 반응이 정상적인지 기준에 따라 측정
> 6. 주변상황 : 시나리오가 실행할 동안 시스템에 놓은 실행 화경
